# AfterCare AI 项目说明

## 1. 项目定位

AfterCare AI（基于 Deep Agents 的企业级智能售后分析与处理平台）是一个面向电商企业售后运营的个人开源项目。它通过可控的 AI Agent 调查订单与售后问题、分析经营数据、检索政策并提出处理建议，同时由确定性的后端规则和人工审批保护敏感业务操作。

项目面向 AI 应用开发工程师、Agent 开发工程师和 Python 后端开发工程师岗位，重点展示真实的软件工程与业务系统能力，而不是单纯展示模型对话或框架调用。

## 2. 长期目标

1. 建立可运行、可测试的订单与售后业务基础系统。
2. 让 Agent 能够完成有计划、有工具调用、有证据链的复杂售后调查。
3. 建立可恢复、可审批、可审计的 Agent 执行流程。
4. 通过可复现评测量化单 Agent 与多 Agent 在正确性、延迟和成本上的差异。
5. 形成能够清楚讲解架构取舍、工程实现和评测结果的作品集项目。

## 3. 核心业务能力

### 售后工单调查

输入一个售后问题或订单编号，系统收集订单、工单、支付/退款记录和适用政策，定位异常原因，并生成带证据的处理建议。

### 批量售后分析

围绕时间范围、商品、投诉原因和供应商进行统计分析，输出可复核的指标、异常线索和报告。

### 方案制定与审批

Agent 可以判断政策适用性并创建建议；实际退款、赔付或状态修改必须经过服务端校验和人工审批。审批后的执行机制与权限模型待确定。

## 4. 系统边界

### 范围内

- 模拟电商订单、商品、售后工单、退款、政策及相关主体数据
- FastAPI 业务接口、数据校验、持久化和测试
- 受控的 Agent 业务查询工具
- Deep Agents/LangGraph 的规划、状态和任务恢复实践
- 证据引用、工具调用日志、审批和权限边界
- 单 Agent/多 Agent 对比评测与可复现部署说明
- 支持演示核心流程的 Web 界面

### 当前不在范围内

- 连接真实电商平台或处理真实客户订单
- 无人工审批的自动退款、赔付或资金操作
- 构建完整 ERP、CRM、客服聊天或仓储系统
- 一开始就采用微服务、复杂事件总线或大规模分布式部署
- 在需求和数据规模未验证前引入 Milvus、Celery 等基础设施
- 用模型生成结果替代确定性的财务对账和权限判断

## 5. 核心原则

- **业务系统优先**：Phase 1 先建立可信的数据和接口，Agent 通过受控工具使用这些能力。
- **证据优先**：结论必须可以追溯到业务记录、政策条款或明确推断过程。
- **安全优先**：模型没有最终业务授权，敏感操作必须经过后端规则与人工审批。
- **渐进式 Agent 架构**：先验证单 Agent 闭环，再以评测结果决定是否拆分 Subagents。
- **状态分离**：业务数据、Agent 运行状态和工作文件分别管理。
- **真实验证**：功能、性能和效果只依据可复现测试或运行记录宣称。
- **适度设计**：只实现当前阶段所需复杂度，为将来保留清晰边界而非提前建设。

## 6. 目标交付物

- 可通过 Docker Compose 复现的应用环境（后续阶段）
- 带迁移、种子数据和测试的 MySQL 业务后端
- 可演示复杂售后调查的 Agent 工作流
- 敏感建议的人工审批闭环
- 可追踪的执行记录和可恢复任务
- 可复现的评测集、基准结果和技术报告
- 面向开发者的架构、运行和演示文档

## 7. 成功标准

项目最终成功不以代码量或 Agent 数量衡量，而以以下证据衡量：

- 新环境可以依据文档启动系统并载入模拟数据；
- 核心 API 和业务规则有自动化测试；
- 给定评测案例时，Agent 能输出可核对的事实、证据和建议；
- 未审批的敏感操作无法执行，并有测试证明；
- 中断任务能够按设计恢复，执行过程可追踪；
- 单 Agent 与多 Agent 的对比采用同一数据集和明确指标；
- 文档描述与实际实现及验证结果一致。

## 8. 当前待确定事项

- 具体电商业务口径、退款类型、投诉分类和 SLA 规则
- 多租户需求、用户与组织权限模型
- MySQL 字段、金额和时间存储规范
- Deep Agents、LangGraph、模型供应商及版本组合
- 政策文档格式、检索方式和引用粒度
- 审批角色、审批级别、执行补偿和幂等策略
- 前端首版范围和任务进度协议
- Agent 评测维度、评分器和目标阈值
