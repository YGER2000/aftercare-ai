# AfterCare AI 开发路线图

> 路线图描述计划，不代表已经完成。实际状态和验证证据以 `PROGRESS.md` 为准。

## 优先级定义

- **P0**：当前阶段验收所必需，缺失则不能进入下一阶段。
- **P1**：重要能力，可在 P0 闭环稳定后完成。
- **P2**：优化或扩展项，只在有真实需求和验证依据时实施。

## Phase 1 — 基础业务系统

### 目标

建立可信、可复现的售后业务数据层和查询 API，为 Agent 提供稳定工具基础。

### 1.1 业务需求与领域建模（P0）

- [ ] Day 1：定义订单、订单项、售后工单、退款、投诉、商品、供应商和政策的业务含义。
- [ ] 走查三个核心场景，识别每一步需要的数据、规则和权限。
- [ ] 确认工单与退款状态机、合法转换和异常分类。
- [ ] 确认部分退款、多次退款、并发申请和渠道回调规则。
- [ ] 确认金额、币种、时间、业务编号、审计和数据保留规范。
- [ ] 更新 `PRD.md`、`DATABASE.md` 和 `DECISIONS.md`，所有剩余问题有明确标记。

验收：至少使用“退款失败调查”“政策资格判断”“30 天投诉分析”三个示例完成纸面走查；核心术语与 Phase 1 范围无自相矛盾。

### 1.2 后端工程初始化（P0）

- [ ] 确认 Python 版本、包管理工具及核心依赖版本。
- [ ] 建立 FastAPI 项目最小结构、配置加载和健康检查。
- [ ] 配置格式化、静态检查、类型检查和 Pytest。
- [ ] 创建环境变量示例，不提交真实密钥。
- [ ] 为健康检查和配置失败编写测试。

验收：新环境按 README 安装后能运行测试并启动 API；健康检查返回明确版本/状态；缺少必要配置时安全失败。

### 1.3 MySQL 模型与迁移（P0）

- [ ] 用 SQLAlchemy 2 实现确认后的最小实体。
- [ ] 创建初始 Alembic 迁移。
- [ ] 为状态、唯一性、外键和金额约束编写测试。
- [ ] 验证空库升级；是否要求降级验证待迁移策略确认。
- [ ] 使用 `EXPLAIN` 检查核心查询索引。

验收：空 MySQL 8 数据库可通过迁移创建一致结构；ORM 与迁移无漂移；关键约束有自动化测试。

### 1.4 可复现模拟数据（P0）

- [ ] 设计不含真实个人信息的种子数据规范。
- [ ] 覆盖正常退款、政策不符、渠道失败、处理中超时和数据缺失等案例。
- [ ] 提供幂等或可重置的导入方式。
- [ ] 固定用于后续 Agent 评测的关键业务编号和预期事实。

验收：在干净数据库中可重复载入相同数据；核心调查案例具备确定的记录链路；重复执行行为符合文档。

### 1.5 查询 API 与测试（P0）

- [ ] 实现订单查询接口及订单项展示。
- [ ] 实现售后工单查询接口及状态历史展示。
- [ ] 实现退款查询接口及失败/处理记录展示。
- [ ] 统一响应、错误、分页和时间格式。
- [ ] 覆盖成功、未找到、非法输入和权限边界测试。

验收：可以通过 API 查询指定订单、关联工单和退款记录；测试在干净环境稳定通过；接口契约有文档。

### Phase 1 完成门槛

- [ ] 核心业务规则和数据模型已经确认并记录。
- [ ] Docker Compose 可启动 Phase 1 所需服务。
- [ ] 数据库迁移和种子数据可复现。
- [ ] 订单、工单、退款 API 可用且自动化测试通过。
- [ ] README、架构、数据库和进度文档与实现一致。
- [ ] 未把 Agent、Redis、Celery 或向量数据库作为 Phase 1 的不必要前置条件。

## Phase 2 — Agent MVP

### 目标

在可信业务 API/Service 之上实现一个有证据、可复核的售后调查闭环。

- [ ] 通过兼容性验证选择并锁定 Deep Agents、LangGraph 和模型相关版本（P0）。
- [ ] 定义 Agent 输入、计划、证据和最终结果 Schema（P0）。
- [ ] 封装最小权限的订单、工单、退款和政策查询工具（P0）。
- [ ] 实现单 Agent 的复杂售后调查闭环（P0）。
- [ ] 实现基础政策存储、版本定位和条款引用（P0）。
- [ ] 展示任务计划、步骤状态和错误（P1）。
- [ ] 增加批量售后统计工具，统计结果由确定性查询产生（P1）。
- [ ] 在有评测基线后引入 Data Analyst 与 Policy Specialist（P1）。

完成门槛：对固定案例输出事实、证据、推断和建议；关键证据可追溯；模型无法直接执行退款；单 Agent 基线可复现。

## Phase 3 — 工程化与可靠性

### 目标

让长任务可恢复、敏感操作可审批、权限与运行状态可追踪。

- [ ] 设计任务状态机、LangGraph 检查点和恢复策略（P0）。
- [ ] 实现人工审批、服务端规则复核和完整审计（P0）。
- [ ] 分离只读/写入工具权限并增加幂等保护（P0）。
- [ ] 建立结构化日志、追踪和用量记录（P0）。
- [ ] 实现超时、有限重试、取消和失败恢复（P1）。
- [ ] 根据并发与执行时间证据决定是否引入 Redis/Celery（P1）。
- [ ] 建立上下文压缩、工作文件隔离和清理策略（P1）。
- [ ] 完成核心安全测试和故障注入（P1）。

完成门槛：任务过程可追踪；中断恢复不会重复敏感副作用；未审批或越权操作被拒绝；错误有可诊断记录。

## Phase 4 — 评测与项目交付

### 目标

形成可复现的效果数据、部署材料和项目演示。

- [ ] 创建版本化评测集和证据级期望结果（P0）。
- [ ] 定义任务成功率、证据正确率、工具错误、延迟、Token 和成本指标（P0）。
- [ ] 在相同模型、工具和数据下对比单 Agent 与多 Agent（P0）。
- [ ] 记录失败案例并完成至少一轮针对性优化（P1）。
- [ ] 完善 Docker Compose、部署、备份和故障排查文档（P0）。
- [ ] 制作可复现演示脚本、架构说明和技术报告（P0）。
- [ ] 评估前端体验与无障碍、响应式表现（P1）。

完成门槛：第三方能按文档复现环境、核心演示和评测；结果包含真实运行条件和限制，不使用虚构指标。

## 暂不排期

- 真实电商平台接入
- Milvus 或其他向量数据库
- 多租户商业化能力
- 自动执行真实退款
- 微服务拆分和 Kubernetes 部署

只有在需求、数据规模或评测结果提供明确依据后，才把这些事项加入阶段计划。
