# AfterCare AI 产品需求文档

> 状态：V0.1 初稿。本文描述目标需求，不代表功能已实现。标注“待确定”的内容将在业务分析或技术设计阶段确认。

## 1. 背景与问题

电商售后调查通常需要在订单、物流、工单、退款和政策等多类信息间反复切换。复杂案例依赖运营人员经验，批量问题分析又需要统计能力。AfterCare AI 希望让 Agent 承担信息收集、分析和建议生成，同时把最终权限保留给确定性的业务系统和人工审批者。

## 2. 目标用户

| 角色 | 主要目标 | 权限边界（初稿） |
| --- | --- | --- |
| 售后运营人员 | 调查工单、核对政策、获得处理建议 | 可查询授权范围内数据并发起建议；能否审批待确定 |
| 售后主管/审批人 | 复核证据、风险与建议，决定是否批准 | 可审批其权限范围内的请求；分级规则待确定 |
| 业务分析人员 | 分析投诉趋势、商品和供应商问题 | 只读聚合与明细范围待确定 |
| 系统管理员 | 管理用户、角色、政策版本和系统配置 | 不因管理员身份自动获得资金操作权限，具体模型待确定 |
| 开发/评测人员 | 复现 Agent 运行并评估效果 | 仅使用模拟或脱敏数据 |

## 3. 核心术语

- **售后工单**：围绕一个订单或订单项提出的退货、退款、投诉等请求；允许范围待确定。
- **退款记录**：退款申请、渠道处理及最终结果的业务记录；是否支持部分退款、多次退款待确定。
- **政策**：判断售后资格、时限、金额和例外条件的版本化规则。
- **调查任务**：一次由用户发起、由 Agent 规划并执行的分析过程。
- **证据**：来自授权工具返回的业务字段、统计结果或政策条款引用。
- **处理建议**：Agent 给出的拟议动作，不等于已执行操作。
- **审批请求**：对敏感建议进行服务端校验后创建的待人工决策记录。

## 4. 核心用例

### UC-01 调查单个售后问题（P0）

用户输入“调查订单 ORD-10086 为什么一直没有退款成功”。系统应：

1. 识别订单及调查意图；
2. 查询订单、相关售后工单与退款记录；
3. 检查数据缺失、状态矛盾和可能的失败原因；
4. 检索适用政策；
5. 输出事实、证据、推断、不确定项和建议；
6. 不执行退款或状态修改。

验收条件：在预置模拟案例上，关键事实可追溯到具体业务记录或政策条款；缺失数据不被虚构；敏感动作仅作为建议。

### UC-02 查询基础业务记录（P0）

用户或受控工具可以按业务标识查询订单、售后工单和退款记录，并获得结构稳定、错误清楚的响应。

验收条件：正常、未找到、非法输入和无权限场景均有自动化接口测试；具体权限模型待确定。

### UC-03 批量售后分析（P1）

用户输入“分析最近 30 天投诉最多的商品，找出主要原因及关联供应商”。系统应明确统计时间窗口、口径与数据来源，返回排名、原因分布、关联供应商和可复核明细。

验收条件：预置数据上的统计结果可由确定性查询复算；Agent 不自行编造指标。投诉定义、并列排名和时区口径待确定。

### UC-04 政策适用性判断（P1）

系统根据订单、商品、售后请求和指定时点检索当时有效的政策版本，列出适用条款、满足/不满足条件和信息缺口。

验收条件：输出包含政策版本与条款引用；冲突政策和例外规则的优先级待确定。

### UC-05 创建并审批处理建议（P1）

Agent 提交结构化建议，后端验证业务规则后创建审批请求。审批人查看证据、风险和建议，执行批准或拒绝。批准是否自动触发模拟执行待确定。

验收条件：未审批、越权、重复和已失效请求不能执行；状态变化有审计记录。

### UC-06 任务追踪与恢复（P1）

用户可以查看调查任务的步骤、工具调用状态和最终结果；可恢复的任务在中断后从安全检查点继续。

验收条件：不得重复执行已完成的敏感动作；检查点粒度和恢复策略待确定。

## 5. 业务流程

### 5.1 调查流程

```text
用户提交问题
  -> 服务端鉴权与输入校验
  -> 创建调查任务
  -> Agent 制定/更新计划
  -> 通过只读工具收集业务数据与政策
  -> 校验证据完整性
  -> 生成事实、推断、风险与建议
  -> 保存结果和执行记录
  -> 用户查看结果
```

失败时应保留已经确认的步骤和错误信息。超时、重试次数、用户取消和恢复规则待确定。

### 5.2 审批流程

```text
Agent 形成敏感处理建议
  -> 后端重新校验资格、金额、状态与权限
  -> 创建审批请求
  -> 审批人批准/拒绝/要求补充材料（待确定）
  -> 执行前再次校验业务状态
  -> 调用受限执行服务（后续阶段）
  -> 记录结果与完整审计信息
```

模型不得直接进入“执行”节点。审批有效期、多人审批、撤回和补偿策略待确定。

## 7. 非功能需求

- **安全性**：默认拒绝未授权访问；敏感操作使用最小权限、人工审批、服务端校验和审计。
- **正确性**：业务状态与金额计算采用确定性逻辑；Agent 负责调查和建议，不作为最终事实数据库。
- **可解释性**：调查结果区分工具事实、政策依据、模型推断和建议。
- **可测试性**：业务规则、API、工具契约、Agent 场景和审批安全边界均可自动验证。
- **可恢复性**：长任务能够保存状态；具体恢复目标待确定。
- **可观测性**：记录任务步骤、工具输入输出摘要、错误、模型/工作流版本、延迟及用量；敏感字段脱敏规则待确定。
- **可维护性**：模块职责清晰，文档与迁移同步，小步演进。
- **性能与可用性**：响应时间、并发量、数据规模和服务等级目标待基准测试后确定。

## 8. Phase 1 产品验收

1. 业务规则和核心术语经过确认，未决问题有负责人或后续任务。
2. MySQL 模型覆盖订单、订单项、售后工单、退款记录及必要关联实体。
3. Alembic 可在空数据库上创建结构，模拟数据可重复导入。
4. API 能查询指定订单、售后工单和退款记录。
5. 自动化测试覆盖成功、未找到、非法输入和关键状态约束。
6. README 提供可复现的本地启动和验证步骤。

## 9. Day 1 待确认问题

- 售后请求按订单还是订单项发起，是否允许一单多工单？
- 退款是否支持部分退款、多次退款、原路退回及渠道异步回调？
- 订单、工单和退款的最小状态集合与合法转换是什么？
- “退款一直未成功”的标准调查口径和异常分类是什么？
- 投诉与普通退货退款是否为同一实体或独立记录？
- 商品与供应商是当前关系还是需要保留历史供货关系？
- 政策按平台、店铺、商品类目或商品生效，如何处理版本和优先级？
- 首版是否需要用户、角色和组织隔离，还是仅用模拟身份？
- 金额、币种、时区、软删除和审计字段采用什么统一规范？
