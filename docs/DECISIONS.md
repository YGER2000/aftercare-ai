## ADR-001：按“业务系统优先”分阶段开发

- 日期：2026-10-09
- 状态：已接受

### 背景

Agent 的调查质量依赖稳定的数据模型、业务规则和查询能力。如果先编排 Agent，再补业务系统，会让提示词承担本应由后端保障的正确性和权限责任。

### 候选方案

1. 先搭建多 Agent 演示，再逐步补充业务数据和后端；
2. 同时开发完整前后端、Agent 和基础设施；
3. 先完成最小业务系统，再建立单 Agent 闭环并逐步工程化。

### 决定

选择方案 3。Phase 1 先实现业务模型、模拟数据、查询 API 和测试；Phase 2 再接入 Agent。

### 理由

该顺序能让工具和评测建立在确定事实之上，降低并行建设造成的返工，也更清楚地展示 Python 后端与业务建模能力。

### 影响

初期不会出现可对话的 Agent 演示；Phase 1 的验收重点是业务 API 与数据正确性。

## ADR-002：先实现单 Agent，再用评测决定是否引入 Subagents

- 日期：2026-10-09
- 状态：已接受

### 背景

多 Agent 可以隔离上下文和角色，但也增加协调、延迟、Token、失败处理和调试成本。

### 候选方案

1. 从第一版开始使用 Orchestrator、Data Analyst 和 Policy Specialist；
2. 只构建单 Agent，永不拆分；
3. 先构建单 Agent 基线，对复杂任务评测后按需拆分。

### 决定

选择方案 3，保留单 Agent 与多 Agent 的同条件对比能力。

### 理由

避免为了架构展示而增加复杂度，同时能用真实数据说明 Subagents 是否改善正确性或可维护性。

### 影响

Agent 工具和结果 Schema 需要保持清晰边界，以便未来复用；Subagents 不属于首个 Agent MVP 的前置条件。

## ADR-003：敏感操作由后端规则与人工审批控制

- 日期：2026-10-09
- 状态：已接受

### 背景

退款、赔付和业务状态修改可能造成资金与合规风险。模型输出具有概率性，提示词不能构成可靠授权边界。

### 候选方案

1. Agent 获得数据库写权限并自行判断执行；
2. Agent 调用写入工具，完全依赖提示词限制；
3. Agent 只生成结构化建议，由后端校验并进入人工审批，执行前再次验证。

### 决定

选择方案 3。

### 理由

确定性校验、最小权限、人工决策、幂等和审计共同形成可测试的安全边界。

### 影响

需要独立设计建议、审批、执行和审计状态；Agent 的“建议成功”不得展示成退款“执行成功”。

## ADR-004：以模块化单体作为初始系统形态

- 日期：2026-10-09
- 状态：已接受

### 背景

项目当前由个人开发，业务边界和负载均未验证。提前使用微服务、复杂消息基础设施会增加部署和一致性成本。

### 候选方案

1. 按领域拆分微服务；
2. 使用模块化单体，保持 API、应用服务、领域、数据访问和 Agent 的逻辑边界；
3. 将全部逻辑集中在少量路由和 Agent 提示词中。

### 决定

选择方案 2。

### 理由

它能以较低成本保持可测试边界，并允许将来在出现明确扩展需求时拆分。

### 影响

后端首版部署为一个主要应用进程；Redis、Celery、独立 MCP 服务等只在有证据时引入。
